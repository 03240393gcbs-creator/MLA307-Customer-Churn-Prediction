## 1. Project Overview

This project investigates customer churn prediction using sequential customer activity data from a music-streaming service. The objective is to determine whether customers' historical listening activity and interactions can help identify customers who record a cancellation event later in the available observation period.

The project uses the Mini Sparkify event dataset and compares recurrent neural network models with a logistic regression baseline. The results are intended to demonstrate how sequence modelling can support business intelligence and customer retention decisions.

## 2. Project Objectives

The main objectives are to:

- Identify customer churn as a real-world business problem.
- Prepare historical customer event data for sequential modelling.
- Construct fixed-length customer activity sequences.
- Implement and evaluate Simple RNN, GRU and LSTM models.
- Compare the selected recurrent model with logistic regression.
- Evaluate performance using suitable classification metrics.
- Interpret the findings and recommend possible customer retention strategies.

## 3. Dataset

The project uses the Mini Sparkify event dataset, `mini_sparkify_event_data.json`, associated with Udacity's Sparkify project materials.

The dataset contains event-level information such as customer identifiers, timestamps, session identifiers, page events and song metadata.

The current sequence-preparation script uses a fixed prediction cutoff of **3 November 2018**. Customers who had already recorded a cancellation on or before that date are excluded from the eligible prediction cohort.

A customer is labelled as a future churner if a `Cancellation Confirmation` event occurs after the cutoff and by the end of the available dataset. Customers without a recorded cancellation during that period are labelled as non-churners for the observed prediction period.

The final customer count, class distribution and train, validation and test sizes are generated by the preparation script. These values should be taken from the latest execution rather than assumed in advance.

## 4. Data Preparation and Sequential Features

The `prepare_sequences.py` script prepares the data for modelling.

The main preprocessing steps are:

1. Load the JSON event data and remove records with missing or unusable customer identifiers, timestamps or page values.
2. Convert timestamps into dates and define the fixed prediction cutoff.
3. Identify eligible customers and create future-churn labels.
4. Aggregate customer activity into daily features using events available on or before the cutoff.
5. Construct a 30-day sequence for each eligible customer.
6. Represent days without recorded activity using zero-valued rows.
7. Split customers into training, validation and test sets using stratified sampling and `random_state=42`.
8. Fit a `StandardScaler` on active-day observations from training customers and apply the fitted scaler to the other partitions.
9. Calculate class weights from the training labels to address class imbalance.

Each customer sequence contains **30 time steps and 13 daily features**:

| Feature group | Features |
|---|---|
| Overall activity | `event_count`, `sessions`, `songs`, `minutes_listened` |
| Customer interactions | `thumbs_up`, `thumbs_down`, `add_to_playlist`, `add_friend` |
| Service and subscription activity | `roll_advert`, `downgrade`, `upgrade`, `home`, `errors` |

The resulting model input has the shape `(30, 13)` for each customer.

## 5. Models

### 5.1 Simple Recurrent Neural Network (Simple RNN)

The Simple RNN provides a recurrent baseline for learning relationships between daily customer activity observations.

### 5.2 Gated Recurrent Unit (GRU)

The GRU uses gating mechanisms to learn temporal relationships in sequential data. Its architecture is evaluated using different recurrent-unit sizes, dropout rates and learning rates.

### 5.3 Long Short-Term Memory (LSTM)

The LSTM uses gated memory cells to learn longer-term dependencies in sequential customer behaviour. Its configurations are evaluated alongside the GRU configurations.

### 5.4 Logistic Regression Baseline

Logistic regression provides a conventional classification baseline. Each customer's 30-day sequence is flattened into a single feature vector before training. The implementation uses L2 regularisation, `C=0.1`, class weighting and a maximum of 2,000 iterations.

### 5.5 Training Procedure

The recurrent models use a Dense layer with 16 ReLU units and a sigmoid output layer to estimate the probability of future churn. Training uses binary cross-entropy, the Adam optimizer, class weights and early stopping based on validation loss.

The training script tunes GRU and LSTM configurations, compares validation performance across random seeds, and saves the selected recurrent model. The final selected architecture and configuration must be reported from the actual training output.

## 6. Model Evaluation

The project uses the following evaluation measures:

- **Accuracy:** Proportion of correctly classified customers.
- **Precision:** Proportion of predicted churners who are actual future churners.
- **Recall:** Proportion of actual future churners correctly identified.
- **F1-score:** Harmonic mean of precision and recall.
- **ROC-AUC:** Measures the model's ability to rank future churners above non-churners across classification thresholds.
- **Confusion matrix:** Summarises true negatives, false positives, false negatives and true positives.

The evaluation script selects the final sequence model's classification threshold using validation-set F1-score, prioritising higher recall and then a higher threshold when scores are tied. Logistic regression uses a threshold of 0.50.

The held-out test set is used for final evaluation, not for selecting the sequence model's threshold.

Five-fold stratified cross-validation is also implemented in `cv.py`. It reports out-of-fold ROC-AUC for configured GRU and LSTM models, a smaller GRU configuration and logistic regression. These cross-validation results are reported separately from the final test-set results.

## 12. Business Interpretation

The purpose of the project is to investigate whether historical customer activity can help identify customers who record cancellation events during the observed future period.

If the results support further investigation, the predictions could help a music-streaming business prioritise customers for human-reviewed retention outreach. Recall can indicate how many future churners are identified, while precision can help estimate how many customers contacted may actually be at risk.

A business should test any retention intervention through a controlled pilot before claiming that the model reduces churn or improves revenue.

## 13. Limitations

The project has several limitations:

- The dataset covers a limited observation period.
- A customer labelled as a non-churner may cancel after the dataset ends.
- Customers who cancelled on or before the cutoff are excluded from the prediction cohort.
- A relatively small cohort and class imbalance may make performance estimates unstable.
- The feature set focuses on daily activity and does not include all possible billing, support or customer-profile information.
- The model evaluates recorded future cancellation events; it does not establish the cause of churn.
- Offline test performance does not demonstrate that a retention campaign will improve business outcomes.

The findings should therefore be interpreted cautiously and validated using additional data before real-world deployment.
